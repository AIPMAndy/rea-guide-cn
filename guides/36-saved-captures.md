## 你要解决的具体问题

从脱敏记录建立事件因果链，而不是依赖黑箱分析。建议先做一个自己编译、能够公开完整输入输出的样例。REA 上游列出的能力可能尚未进入正在使用的 npm 版本，必须检查本机的 `rea --help`、`rea capabilities` 或所安装包实际清单。

## 环境与授权检查

- [ ] 文件来源、授权范围、版本、SHA256 和可公开的输出边界已记录。
- [ ] 已确认此类型在 **当前已安装发行版** 可用，而非仅在 GitHub 主分支存在。
- [ ] 若需要外部工具，单独核对系统支持、许可证、版本和工具链安装方式。
- [ ] 只读为默认模式；运行、提取、文件改动、捕获流量前单独审批。

## 六步完整流程

### 步骤 1｜仅使用自己生成的无账号网络请求记录或合成崩溃数据。

### 步骤 2｜检查 HAR、PCAP、日志中是否有 cookie、Authorization、URL token、手机号或地址，先脱敏后入库。

### 步骤 3｜按真实文件类型选择官方支持的 HAR/SAZ、TShark、pwntools 等路径；操作系统依赖不同。

### 步骤 4｜记录时间范围、请求方法、响应状态、错误信号及进程信息，同时保存源记录哈希。

### 步骤 5｜区分网络记录证明发生过的请求与“应用为何发请求”的推断。

### 步骤 6｜编写反证：如果是代理、缓存、重试或采样丢失，当前归因是否仍成立。

## 证据与推断对照表

| 结论 | 原始证据 | 验证方法 | 允许的表述 |
|---|---|---|---|
| 支持该类型的检查 | 当前版本的 `--help` / 实际返回 | 本机查看、保留退出码 | 本机版本已证实 / 未验证 |
| 样本包含特定结构 | 本地测试文件、偏移或元数据输出 | 对照自己编译的样例 | 直接观察；不得推演完整业务逻辑 |
| 推断程序行为 | 静态关系或元数据 | 独立运行样例与边界测试 | 假设，需进一步证实 |

## 失败场景与红队审核

**主要风险：**抓包记录可能没有完整请求上下文，误将重试当首次事件。

- 若无法找到真实来源/数据，应标明“未验证”，不得由 AI 补造文件位置或函数地址。
- 不能依赖某个工具的“成功”字符串证明真实业务结果；重要结论需以自有样例复验。
- 避免在 GitHub Issue 分享未脱敏的原始程序、截图、网络载荷、密钥与合同资料。
