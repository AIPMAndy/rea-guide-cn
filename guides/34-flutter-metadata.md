## 你要解决的具体问题

只用公开的编译标识研究 Flutter 样例。建议先做一个自己编译、能够公开完整输入输出的样例。REA 上游列出的能力可能尚未进入正在使用的 npm 版本，必须检查本机的 `rea --help`、`rea capabilities` 或所安装包实际清单。

- [ ] 若需要外部工具，单独核对系统支持、许可证、版本和工具链安装方式。
- [ ] 只读为默认模式；运行、提取、文件改动、捕获流量前单独审批。

## 六步完整流程

### 步骤 1｜自行构建包含一个公开页面的 Flutter 测试 APK，记录 Flutter/Dart SDK 版本。

### 步骤 2｜计算测试 APK 文件哈希，分开记录 APK 包体和内部 ELF/资源身份。

### 步骤 3｜查阅官方 Flutter 静态解析支持范围，确认无须执行 APK 的文件头线索。

### 步骤 4｜提取 Dart snapshot hash、ABI 库摘要与 engine build provenance 中能直接证明的字段。

### 步骤 5｜将不同编译版本的测试包做对比，不把哈希差异直接等同于业务逻辑差异。

### 步骤 6｜输出静态证据和版本依赖，不试图获取其他 App 的受保护业务数据。

## 证据与推断对照表

| 结论 | 原始证据 | 验证方法 | 允许的表述 |
|---|---|---|---|
| 支持该类型的检查 | 当前版本的 `--help` / 实际返回 | 本机查看、保留退出码 | 本机版本已证实 / 未验证 |
| 样本包含特定结构 | 本地测试文件、偏移或元数据输出 | 对照自己编译的样例 | 直接观察；不得推演完整业务逻辑 |
| 推断程序行为 | 静态关系或元数据 | 独立运行样例与边界测试 | 假设，需进一步证实 |

## 失败场景与红队审核

**主要风险：**snapshot hash 与 engine build 线索不足以恢复完整 Flutter 源代码。

- 若无法找到真实来源/数据，应标明“未验证”，不得由 AI 补造文件位置或函数地址。
- 不能依赖某个工具的“成功”字符串证明真实业务结果；重要结论需以自有样例复验。
- 避免在 GitHub Issue 分享未脱敏的原始程序、截图、网络载荷、密钥与合同资料。
